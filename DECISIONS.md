## Арт-дирекшн: «Signal Cosmos»

**Ідея.** Всесвіт — це нейромережа студії.

- Вузли — можливості.
- Лінії — інтеграції.
- Імпульси, що біжать лініями, — дані.

Візуал показує саме те, що студія продає: з'єднання систем в одне ціле.

### Типографіка

Шрифти підключаються через `next/font/google`, файли self-hosted.

| Роль            | Шрифт                         | Деталі                                                                        |
| --------------- | ----------------------------- | ----------------------------------------------------------------------------- |
| Заголовки       | **Unbounded** (variable)      | широкий футуристичний; subsets latin, latin-ext, cyrillic                     |
| Текст           | **Manrope** (variable)        | subsets latin, latin-ext, cyrillic                                            |
| Мікролейбли HUD | **JetBrains Mono** (variable) | лише latin: цифри, індекси, коди. Кириличний текст цим шрифтом не набирається |

Літери ą ę ł ż ź ś ć ń ó та ї є ґ і перевіряються на скріншотах. Запасний шрифт для заголовків — Geologica.

### Мотиви UI

- Тонкі кутові скоби-рамки.
- Лінії-виноски від об'єкта до підпису.
- Ретикл навколо об'єкта у фокусі.
- Розріджена типографіка великими літерами.
- Моно-індекси «01 / 05».
- Скляні панелі. Жодних «карток із тінню».

### Характер руху

Важкий і спокійний.

- Дрейф ледь помітний.
- Польоти камери: power3/expo inOut, 1,4–1,8 с.
- Hover-реакції: 150–200 мс.
- Без пружин і «підстрибувань».
- UI з'являється як fade + 8px + легкий blur за 250 мс.
- Reduced-motion: crossfade 300 мс, без автоповороту і без FOV-punch.

## Рішення

**D01. Версії стеку.**

- Next 16.4, React 19.3, three 0.187, R3F 9.8, drei 10.7, postprocessing 3.2/6.39, next-intl 4.15, Tailwind 4.3, zod 4.6, zustand 5.1, Vitest 5.1.
- **TypeScript 6.0, а не 7.** typescript-eslint 8.x підтримує TS до 6.1.
- **ESLint 9.39, а не 10.** eslint-plugin-react, jsx-a11y і import з eslint-config-next мають peer-залежність `eslint ≤ 9`. npm позначає ESLint 9 як deprecated. Переходимо на 10, щойно eslint-config-next його підтримає.

**D02. Статичний хостинг GitHub Pages.**

- `output: 'export'`, `trailingSlash: true`, `images.unoptimized: true`.
- Без proxy/middleware і без route handlers.
- `/` — статична сторінка з meta refresh, JS-redirect на `/pl/` і canonical на `/pl/`.

**D03. Base path і URL сайту.**

- `NEXT_PUBLIC_BASE_PATH` (нормалізується в `src/lib/base-path.ts`) задає `basePath` і `assetPrefix`.
- `NEXT_PUBLIC_SITE_URL` — повний публічний URL кореня сайту разом із basePath. Workflow бере його з `actions/configure-pages` (`base_url`).
- Якщо змінна не задана, береться `https://<domain>` з `site.config.ts`, коли домен справжній, інакше `http://localhost:3000`.
- Шляхи поза `next/link` будуються через `withBasePath()`.

**D04. CNAME.** При деплої через GitHub Actions файл CNAME не потрібен: GitHub його ігнорує, а домен задається в Settings → Pages. Для сумісності `scripts/postbuild.mjs` усе одно створює `out/CNAME`, якщо задано змінну `PAGES_CNAME`.

**D05. Словники розділені.**

- `messages/<locale>/ui.json` — рядки інтерфейсу.
- `messages/<locale>/content.json` — тексти категорій, послуг і кейсів.

Для next-intl обидва файли зливаються в одне дерево. Повні словники використовуються лише на сервері (`src/i18n/messages.ts`). Клієнт отримує тільки вибрані простори імен через `NextIntlClientProvider` або готові рядки через props.

**D06. Доступ до текстів контенту.** Тексти читаються через `src/lib/content-text.ts`, який валідує їх zod-схемою. Відсутній текст ламає збірку. Типізовані `t()`-ключі використовуються для статичних UI-рядків.

**D07. Слаги.** Англійські й однакові для всіх мов (`/pl/services/web/landing-pages/`), як у брифі.

**D08. URL — єдине джерело правди про стан сцени.**

- `routeToSceneState()` — чиста функція з тестами.
- Zustand зберігає лише перехідний стан: підсвічування, якість, прогрес переходу, вибір конфігуратора.

**D09. Маніфест сцени.** Він збирається на сервері для кожної мови (`buildSceneManifest`) і передається в Canvas як prop. Так у браузер не потрапляють повні словники й чернетки кейсів.

**D10. Шейдери** пишуться як TS-модулі з template strings (`/* glsl */`). Окремі loader-и для Turbopack і Vitest не потрібні.

**D11. Детермінована випадковість** (`src/scene/random.ts`, mulberry32). Процедурна геометрія однакова при кожному візиті, а рендер лишається чистим: правило `react-hooks/purity` забороняє `Math.random()` під час рендеру.

**D12. Видимість кейсів.** Чернетки видно, коли `NODE_ENV !== 'production'` або `SHOW_DRAFTS=true` (`shouldShowDrafts()` у `content/index.ts`). У продакшн-збірці лишаються тільки `published`.

**D13. Мова документації.**

- PROGRESS.md, DECISIONS.md, REPORT.md, CONTENT_REVIEW.md і docs/ пишуться українською, бо їх читає замовник.
- README.md і визначення агентів у `.claude/agents/` — англійською, як код (технічна аудиторія та інструкції моделям).

**D14. Формулювання гендерно-нейтральні** в усіх мовах: без «chciałbym/chciałabym», «зробив/зробила» тощо.

**D15. Зміна мови.** Перевірено qa-reviewer у M1.

- Перемикання мови — це м'яка навігація без перезавантаження документа: оновлюються `lang`, HUD і title.
- Canvas при цьому перемонтовується, бо змінюється сегмент `[locale]`. З'являється новий WebGL-контекст, fade-in повторюється.
- За 20 перемикань ніколи не лишалося більше одного canvas, попереджень про контексти не було.
- Це прийнятно: мову змінюють рідко, а стан сцени відновлюється з URL.

**D16. Навігація між сусідніми планетами** стрілками й свайпом робить `router.replace`, тому «назад» повертає до системи. Клік по планеті робить `push`.

**D17. Git.** Репозиторій новий і без remote, тому коміти йдуть одразу в `main` після кожного блоку. Пуш — коли замовник додасть remote.

**D18. Розширення зон відповідальності агентів.** У таблиці з брифу ці файли не закріплені.

- `ui-engineer` володіє кореневими конфігами (`package.json`, `next.config.ts`, `tsconfig.json`, eslint, prettier, vitest і playwright конфіги), а також `.github/`, `public/`, `README.md`, `content/schema.ts` і `content/index.ts`.
- `ui-engineer` може додавати нові ключі в `messages/*/ui.json` з чернетками трьома мовами. Ключі мають бути однаковими в усіх мовах, а нові ключі він перелічує у звіті. `content-writer` потім вичитує їх.
- `scene-engineer` може змінювати значення візуальної ДНК (`dna`, `planet`) у `content/categories.ts`. Структуру схеми змінює лише `ui-engineer` за погодженням з оркестратором.
- Оркестратор веде `PROGRESS.md`, `DECISIONS.md`, `REPORT.md` і `docs/`.

**D20. Портфоліо — опційний catch-all `portfolio/[[...project]]`.** Під `output: 'export'` Next 16.4 відхиляє порожній `generateStaticParams` («returned an empty array»), а в продакшні опублікованих кейсів немає. Один маршрут віддає список (`project: []`) і сторінки видимих кейсів, тому в `out/` немає ні заглушок, ні чернеток. З `SHOW_DRAFTS=true` з'являються сторінки кейсів.

**D21. Стратегія завантаження шрифтів.** Усі шрифти variable. `subsets` у next/font визначає лише preload, а `@font-face` з `unicode-range` генеруються для всіх subset-ів.

- Preload: Unbounded latin і Manrope latin + latin-ext. Це 3 файли, 88,4 KB замість 7 файлів і 287,6 KB за замовчуванням.
- Unbounded latin-ext і кирилиця обох шрифтів підвантажуються на вимогу.
- JetBrains Mono (latin) без preload.
- Варіант зі статичним накресленням Unbounded 500 зекономив би близько 96 KB для польських заголовків, але бриф вимагає variable. Переглянемо, якщо цього вимагатиме бюджет продуктивності.
- Перевірка покриття: `npm run fonts:report`.

**D22. Обхід бага Next 16.4.6 на Windows.** Під час статичного експорту prefetch-файли сегментів пишуться у вкладені теки (бекслеші від `path.relative`), а клієнт запитує плоскі імена.

- `scripts/postbuild.mjs` «сплющує» ці файли. На Linux (CI) це no-op.
- Обхід прибрати, коли Next виправить `convertSegmentPathToStaticExportFilename`.

**D23. Vitest 5 і мала літера диска.** Коли шлях до репозиторію має малу літеру диска (`d:\`), Vitest 5 падає: завантажуються дві копії раннера. Обгортка `scripts/vitest.mjs` нормалізує літеру диска; `npm test` іде через неї.

**D24. next-intl на статичному хостингу.**

- `localeCookie: false`, бо cookie ніхто не читає.
- `timeZone: 'Europe/Warsaw'`, щоб форматування на сервері (під час збірки) і в клієнті збігалося.

**D25. Ідентифікатори підсвічування** (`category:<id>`, `service:<cat>/<slug>`, `portfolio`, `configurator`, `project:<slug>`) живуть у `src/scene/node-ids.ts`. Цей модуль не імпортує three.js, тож UI використовує його без збільшення бандла.

**D26. Огляд всесвіту на телефоні.** Оновлено після D28.

- Напрям огляду вибирається за пропорціями вільної області (`safeRect`), а не всього в'юпорта.
- На головній на телефоні вільна смуга над hero ширша, ніж висока. Тому в кадрі всі 7 вузлів, разом із портфоліо, і розмір вузлів від цього не страждає.
- Портретний огляд без портфоліо лишається лише для високих кадрів (`safeRect = null`).

**D27. Контракт клавіатури й кліків між UI і сценою.**

- UI, що «споживає» Esc (меню), викликає `preventDefault()`. Обробники Esc і «назад» у сцені ігнорують події з `defaultPrevented`.
- Навігація з вузлів сцени спрацьовує на `click`, а не на `pointerup`, бо закриття меню поглинає наступний `click`.

**D28. Контракт `safeRect` між UI і камерою.**

- UI-шар публікує в `src/store/scene.ts` прямокутник в'юпорта, не закритий HTML-оверлеями поточного маршруту: HUD, hero, панель, bottom sheet. Значення в CSS px.
- Камера кадрує фокус усередині цього прямокутника (зсув головної точки, підгонка під менший бік).
- Зміни `safeRect` згладжуються, при reduced-motion застосовуються одразу.
- Причина: у M1 рецензенти виявили, що вузли й системи опиняються під hero, панеллю або sheet (QA M1-03, visual V-01 і V-02).
- Реалізація:
  - `camera.setViewOffset` переносить головну точку в центр rect, а дистанція підганяється під його розміри (`camera/goals.ts`, чисті функції з тестами);
  - зміни перших 0,5 с (fade-in) застосовуються одразу;
  - на телефонах UI не публікує проміжний `null` між маршрутами;
  - у M2 CameraControls `fitToSphere` не використовуємо, бо він ігнорує view offset; лишається власний fit.
- Ціна: на desktop-головній вузли приблизно вдвічі менші, бо вільна область становить близько половини екрана. У M2 можна повернути до 14 %.

**D30. Попередження THREE.Clock.** Його виводить R3F 9.8.2: він створює `THREE.Clock`, який three 0.187 позначає як deprecated. Наш код тут ні до чого, а 9.8.2 — остання версія 9.x.

- Фільтруємо рівно одне повідомлення через офіційний хук three `setConsoleFunction` (`src/scene/three-console.ts`). `console` не патчиться.
- Фільтр прибрати, коли вийде R3F з `THREE.Timer`.

**D31. Межа кількості категорій.** У всесвіті може бути до 30 категорій (`MAX_CATEGORY_NODES`). Якщо їх більше, у dev збірка падає з помилкою, а в production з'являється `console.error` і відображаються перші 30.

**D32. Помилки сцени.**

- Невдале завантаження чанка сцени → сторінка працює без 3D: `import().catch` рендерить замість сцени порожній компонент. Повторної спроби немає, бо Turbopack кешує відхилений чанк.
- Помилка рендеру → `SceneErrorBoundary` один раз перемонтовує сцену через 1,5 с, а після повторної помилки вимикає 3D.

**D29. Анімації HTML під час переходів.**

- Під час клієнтської навігації панелі з'являються як fade + 8px + blur за 250 мс.
- Hero на головній показується після того, як політ камери пройшов приблизно 60%.
- На першому завантаженні будь-якого маршруту анімацій і затримок немає, щоб не погіршувати LCP.

**D33. Хто публікує `safeRect`.**

- Оверлеї позначаються атрибутом `data-scene-overlay`: HUD, hero, індекс категорій, панель або sheet.
- `SafeAreaPublisher` рахує найбільший вільний прямокутник (`src/lib/safe-rect.ts`, чиста функція з тестами). Оцінка — за тим, наскільки великий бокс 1,5:1 (landscape) або 1:1 (portrait) вміщується в прямокутник. Значення в цілих пікселях.
- Перерахунок на resize, зміну маршруту, зміну розміру оверлея й кінець вхідної анімації. Покадрового оновлення немає.
- Тимчасові оверлеї (меню «Послуги», мобільне меню) свідомо не враховуються.
- З `?debug=1` прямокутник видно в `window.__safeRect`.

**D34. Тексти `global-error.tsx`.** Цей компонент потрапляє в базовий чанк кожної сторінки, тому словники він не імпортує. Простір імен `error` з усіх `ui.json` вбудовується під час збірки через `env.GLOBAL_ERROR_TEXTS` у `next.config.ts`, це близько 1 KB. Мова визначається за шляхом.

**D35. Типографіка.**

- Тексти контенту (один раз на мову), а також UI-заголовки й ліди обробляються `bindShortWords`: після однолітерних слів у pl і uk ставиться нерозривний пробіл.
- У словниках NBSP вручну не ставимо.
- У M4 генератор Telegram-повідомлення має замінювати U+00A0 на звичайний пробіл, щоб не роздувати бюджет URL.

**D36. Кольори.**

- Кольори категорій беруться лише з ДНК у `content/categories.ts`; токени категорій із CSS прибрано.
- Бренд-акцент UI — окремий токен `--color-brand`, плюс `--color-nebula` для фону.
- Колір портфоліо має одне джерело: `PALETTE.portfolio` у `src/scene/config.ts`.

**D37. Дублікати 404 у збірці.** Postbuild видаляє `out/404/` і `out/_not-found/`, бо GitHub Pages віддавав би їх зі статусом 200. Для невідомих шляхів лишається єдиний `404.html`.

**D38. Апостроф в українських текстах — `’` (U+2019).**

- Він типографічно правильний і гарантовано є в Manrope та Unbounded. Символ `ʼ` (U+02BC) у шрифтах не гарантований.
- ASCII-апостроф `'` в ICU-синтаксисі next-intl слугує escape-символом і перед `{`/`}` ламає повідомлення.

**D39. `AGENTS.md` від Next 16.** Цей блок правил для AI-агентів генерує `next dev`: він відсилає до документації в `node_modules/next/dist/docs/`. Файл закомічено. Next сам радить так робити: інакше `next dev` щоразу відтворює незакомічену зміну, а вміст корисний для агентів, які працюють із Next 16.

**D40. Панелі на телефонах у landscape.**

- Рішення: коли висота не більша за 30rem, а ширина не менша за ~34rem, використовуємо бічну панель. Bottom sheet лишається для портретних телефонів (вимога брифу).

- Tailwind-варіанти `short:` (висота до 30rem) і `shorter:` (до 22,5rem).
- На коротких в'юпортах hero компактний, ліворуч; категорії в один рядок; hero обмежений висотою під HUD.

**D19. Debug-хук сцени.** Якщо в URL є `?debug=1`, сцена публікує `window.__sceneStats`: draw calls, трикутники, програми, геометрії, текстури, час кадру. Через нього рецензенти порівнюють продуктивність у headless-браузері. В інших випадках хук нічого не робить.

**D42. Esc → батьківський маршрут (уточнення D27).**

- Обробник `EscapeToParent` (UI) слухає `keydown` на `window` у фазі bubble і пропускає події з `defaultPrevented`.
- Якщо Navigation API показує, що попередній запис історії і є батьківським маршрутом, викликаємо `router.back()`; інакше робимо `push` батьківського шляху.
- Сцена власного Esc → back не має. Якщо сценний обробник поглинає Esc, він зобов'язаний викликати `preventDefault()`.

**D43. Exit-фейд через «привиди», а не View Transitions.**

- Перед заміною вихідний hero або панель клонується в «привид»: `inert`, без `id`, згасає за 150 мс. Клон створює MutationObserver.
- Чому не View Transitions: вони блокують введення на час переходу, заморожують знімок сторінки разом із WebGL і в Next 16 потребують експериментального прапорця.
- Під reduced motion привидів немає, лише простий фейд.
- Якщо попередня зміна маршруту сталася менш ніж ~250 мс тому, вхідна анімація ще йде, тож привид не створюємо.

**D44. Поява hero прив'язана до польоту.**

- На клієнтському поверненні додому hero з'являється, коли `flight.progress` досягає 0,6. UI лише підписується на store, без ре-рендерів.
- Захисні межі:
  - до 4 кадрів (не менше 120 мс) чекаємо, поки політ почнеться;
  - якщо прогрес не оновлюється 1,2 с, вважаємо політ завислим;
  - жорстка межа 5 с;
  - під reduced motion — фейд за 150 мс.
- Причина появи записується в `data-reveal-reason`: `flight`, `flight-end`, `no-flight`, `stall`, `timeout` (з `hero-reveal.ts`), а також `reduced-motion` і `no-scene` (з `flight-gate.ts`).
- Під час першого завантаження анімації немає (D29).
- Чому межі такі: у headless SwiftShader при ~5 fps обмеження `dt` розтягує 1,6-секундний політ приблизно до 3,6 с реального часу.

**D45. Хуки для автоматизації.**

**D48. Непрозорий canvas.**

- Фон `.backdrop-cosmos` тепер малюється всередині canvas, кольори беруться з CSS-токенів.
- CSS-фон лишається для простого режиму та для fade-in першого кадру.
- Причина: композитор з alpha отримує пікселі з rgb > alpha. Специфікація WebGL цього не визначає, тож браузери показують таке по-різному.

**D49. Камера.**

- Ввід обробляє drei `CameraControls`. Межі dolly: 0,6–1,4× від підігнаної відстані на огляді, 0,5–1,9× у системі. Pan немає. Обертання одним пальцем, на touch — pinch.
- Польоти — GSAP-таймлайн із каналами look/dolly/orbit/arc/punch/flash. Dolly іде в лог-просторі.
- Занурення: `expo.inOut`, ≈1,7 с. Решта польотів: `power3.inOut`, 1,2–2 с. Є FOV-punch і спалах bloom при прибутті в систему.
- Ввід користувача перериває політ, а згасання CameraControls довозить камеру до цілі.
- Reduced motion: dip на 300 мс зі склейкою посередині.
- Власний fit через safeRect і `setViewOffset` (D28) лишається.
- 3D-hover працює лише за `(hover: hover)`: на телефонах після тапу не лишається підсвічування.

**D50. Автоповорот.**

- Вмикається через 6 с без вводу, на hover стає на паузу.
- На огляді — погойдування ±16° з періодом 70 с, кільце еліптичне. У системі — 1,6°/с.

**D51. Мінімальний розмір ядра.**

- Діаметр ядра на екрані — щонайменше 5 % короткої сторони вільної області (у межах 12–30 px). На desktop home це ≈28 px.
- Маленьким ядрам додаємо яскравості.
- safeRect не змінюємо.

**D52. Прогрів шейдерів.**

- Experience тримає кеш матеріалів; компіляція йде через портал і `compile` з тим самим render target.
- Розклад: idle-колбек через 1,5 с після першого кадру, а також на touchstart і на hover. Реєстр `prewarm/registry.tsx` можна розширювати в M3.
- `compileAsync` викликаємо лише з `KHR_parallel_shader_compile`. Без нього — `renderer.compile()` + `getUniforms()` в idle, щоб і зависання, і попередження three.js не припадали на взаємодію.
- Стан доступний у `window.__scenePrewarm`.

**D53. Якість (уточнено після M2-1).**

- Рівень визначається до першого рендера (за пристроєм або `?quality=`) і в межах сесії лише знижується: `PerformanceMonitor` має тільки `onDecline`, підвищення після зниження немає (P-03). Монітор вмикається через 6 с після появи всесвіту, лише коли frameloop = `always` і рівень не закріплено.
- DPR задає сам проп `dpr` у `<Canvas>`: `min(devicePixelRatio, 2) × частка рівня` (1 / 0,8 / 0,6). Він перераховується при зміні devicePixelRatio. `AdaptiveDpr` прибрано: R3F 9.8 при кожному ре-рендері повертав DPR до значення пропа, тож частка рівня не трималась (P-02).
- Регресу DPR під час руху немає: кожна зміна DPR очищає буфер canvas.
- Bloom вимкнено на low, MSAA 2× лише на high.
- Зміна рівня не перезапускає прогрів усіх систем. Ключі стають «холодними» лише тоді, коли змінюються програми (LOW_QUALITY, bloom). Потім вони компілюються за hover, touchstart або фокусом, а також при зануренні.
- Параметри для перевірок: `?quality=high|medium|low`, `?debug=1&slowmo=N`.

**D54. frameloop.**

- `never` — вкладка прихована.
- `demand` — reduced motion.
- `always` — в інших випадках.

**D55. Власник перевірки WebGL.** `src/lib/webgl.ts` використовує лише `SceneRoot`, тож файл переходить до scene-engineer (розширення D18). Перевірку зроблено дешевою, без тестового контексту: P-01 показав, що тестовий контекст забирав 378 мс гідратації. **D65. Поетапний старт сцени й черга компіляції (P-01b, P-04).**

- Етапи:
  - 0 — фон, зорі, камера;
  - 1 — bloom (окремий lazy-чанк);
  - 2 — всесвіт, змонтований прихованим; програми компілюються через чергу;
  - 3 — поява canvas, далі прогрів і монітор якості.
- Черга компілює один матеріал на idle-слот (`compileAsync`, якщо є KHR_parallel_shader_compile), за пріоритетами: старт > активна система > hover/touch/фокус > сліпий idle.
- Сліпий прогрів стартує через 6 с після появи всесвіту.
- Жорсткий запасний таймер: не пізніше ніж через 1,5 с після першого кадру все монтується й canvas з'являється, навіть якщо черга не завершилась. Скасований або невдалий тікет теж відкриває сцену.
- До легкого режиму в harness (mobile 4×) виміряно TBT 1183 → 490 мс на спокійній машині, найбільша задача сцени ≈440 → 153 мс. Після додавання таймера повторно не вимірювали.

**D66. Чернетка запиту.**

- `src/store/request.ts` зберігає refs послуг `"<категорія>/<slug>"` у порядку додавання, через `safeStorage` під ключем `kabaninno.request.v1` у форматі `{ v: 1, items }`.
- На сервері й під час гідратації store порожній. `RequestSync` у layout читає збережене в ефекті з переліком послуг збірки:
  - невідомі refs відкидаються;
  - додане до гідратації зливається;
  - вкладки синхронізуються через подію `storage`.
- Конфігуратор M4 читає той самий store.

**D67. «Додати до запиту» як перемикач.**

- Без JS лишається посилання на конфігуратор із `?add=`.
- З JS — кнопка з `aria-pressed`. Polite live region повідомляє назву послуги; текст форматується на сервері, тож ICU на клієнті не запускається.
- Поки послуга в запиті, видно посилання «Перейти до запиту».
- Посилання на конфігуратор у HUD і мобільному меню показує бейдж кількості з доступною назвою (видимий текст іде першим).

**D68. Перемикання планет (уточнення D16).**

- Стрілки ←/→ ігноруються з модифікаторами, при повторі клавіші, під час IME, у полях і віджетах зі стрілками, а також коли відкрито діалог або меню HUD.
- Свайп по панелі: від 56 px, горизонтальний рух у 1,6 раза більший за вертикальний, до 700 мс, не ближче 24 px від краю екрана. Панель має `touch-action: pan-y pinch-zoom`.
- Між планетами — `replace`. Із системи (→ перша планета, ← остання) — `push`, як клік по планеті: «назад» повертає до системи.
- Сцена стрілок і свайпу не обробляє.

**D69. Кнопка «← Всесвіт».** Перший елемент breadcrumbs у панелях системи й планети оформлено як окрему кнопку-пігулку: 44 px на телефоні, 36 px на desktop.

**D70. Bottom sheet на телефоні.**

- Ручка — кнопка 44 px з `aria-expanded`. Tap, Enter або Space перемикають стан; drag від 40 px згортає чи розгортає.
- Згорнутий стан займає `min(12.5rem, 45dvh)` і переживає перемикання планет (`store/ui.ts`).
- Висота анімується 300 мс, при reduced motion — миттєво.
- safeRect оновлюється через ResizeObserver.
- Клавіатурний фокус усередині згорнутого sheet розгортає його.

**D71. Реєстри планетарної системи.**

- Ядро → `CORE_STYLES`: 5 окремих DETAIL-шейдерів поверх універсального ядра. При `uDetail=0` вони тотожні йому, тому під час прильоту немає «стрибка».
- Форма → `PLANET_SHAPES`, матеріал → `PLANET_MATERIALS`, супутники → `MOON_SHAPES` + `moonPose`.
- Повноту гарантує `Record` у TypeScript; unit-тест звіряє реєстри з enum схеми.
- Нова категорія чи послуга в `content/` не потребує змін у сцені.

**D72. Світло системи.**

- Єдине джерело світла — ядро (`uCorePos`). Планети мають денну й нічну сторони (wrapped diffuse), rim і відбиття процедурного оточення.
- Стандартні матеріали three не використовуються; кожен шейдер має варіант `LOW_QUALITY`.

**D73. Фокус планети.**

- Планета «паркується»: швидкість плавно падає до 0, камера дивиться на її живу позицію.
- Відстань — reach планети, вписаний у safeRect (`PLANET_FRAMING` 1,35, мінімум 3,2·reach). Напрям — від ядра назовні з легким підйомом.
- Сусідні планети тьмяніють до 32 % і підсвічуються при hover.
- Deep link ставить планету у фазу з DNA.
- Зміни safeRect (bottom sheet) камера відпрацьовує із загасанням.

**D74. Кеш матеріалів системи.**

- `SystemMaterialCache` (власник — Experience) містить і всі матеріали планет. Prewarm компілює їх через чергу по одному на idle-слот, і програми переживають unmount попереднього прогріву.
- Геометрії живуть разом із компонентом і звільняються при unmount.
- Кеш очищується при зміні tier і при unmount сцени.

**D75. Інтерактивність планет.**

- Hit-зони та мітки планет активні лише після завершення польоту в систему (`bus.systemInteractive === категорія`). Фокусована планета хіт-зони не має (QA N3).
- Радіус hit-зони — `max(reach·1,15, 22 px)`.
- Клік із системи — push, із фокусу планети — replace (D16, D68).
- Підсвітка `service:<cat>/<slug>` спільна для HTML-посилань і сцени: орбіта світиться, планета сповільнюється до 0,22, з'являється мітка.

**D76. Мітки (L-02, L-03).** Після завантаження шрифтів мітки перемірюються. Лінії мережі під видимою міткою тьмяніють до 30 %.

**D77. Модель конфігуратора.**

- Ідентифікатори опцій лежать у `content/configurator.ts`. `buildConfiguratorModel` поєднує їх із категоріями контенту; модель — чистий JSON і передається клієнту через props.
- Крок 2 — це послуги вибраних категорій плюс додаткові функції з даних. Нова категорія не потребує змін коду.
- Id функції має вигляд `<категорія>/<ключ>`; для послуги це той самий ref, що в чернетці запиту (D66).
- Бюджети задано діапазонами в PLN (валюта з `site.config`); варіант «не знаю» — `not-sure`.

**D78. Валідація і чернетка конфігуратора.**

- Обов'язково:
  - хоча б один тип;
  - хоча б одна функція вибраних категорій;
  - усі чотири поля бізнесу;
  - бюджет і термін;
  - ім'я 2–80 символів після trim.
- Коментар необов'язковий, до 1000 символів.
- Будь-який попередній крок доступний завжди; наступний — коли всі попередні валідні.
- Чернетка зберігається під ключем `kabaninno.configurator.v1` у форматі `{ v, step, draft }`. При читанні застарілі id відкидаються, а крок відкочується до досяжного.
- Передзаповнення: refs із чернетки запиту і параметр `?add=` вибирають категорію та послугу.

**D79. Повідомлення і бюджет URL.**

- Генератор — чиста функція; усі слова приходять у лейблах.
- Порядок стиснення:
  1. повний формат;
  2. компактний;
  3. обрізання коментаря з «…» по межах графем;
  4. у крайньому разі обрізання всього тексту.
- U+00A0, U+202F і U+2007 замінюються звичайним пробілом (D35).
- Бюджет — 2000 символів на весь URL. Windows обмежує URL при передачі `tg://` у Telegram Desktop (`INTERNET_MAX_URL_LENGTH` = 2083), і це водночас загальна межа сумісності. Українського тексту вміщається близько 330 символів, тому кнопка «Скопіювати текст» показується завжди.

**D80. Надсилання.**

- Інтерфейс `LeadSubmitter`.
- `TelegramLinkSubmitter` будує `https://t.me/<username>?text=…`; якщо текст починається з «@», додається пробіл.
- Username перевіряється; із заглушкою `[TELEGRAM_USERNAME]` лишається тільки копіювання.
- Результат: `opened` або `needs-copy` (`too-long`, `blocked`, `unconfigured`).
- Посилання відкривається справжнім `<a>` або через `window.open` безпосередньо в обробнику кліку, без `noopener` у features; `opener` обнуляється вручну. `tg://` не використовується.
- `ApiSubmitter` надсилає POST із JSON на `NEXT_PUBLIC_API_URL`; поки змінна не задана, кидає зрозумілу помилку. До UI він ще не підключений.
- Буфер обміну: спершу Clipboard API, далі прихована textarea з `execCommand('copy')`.

**D81. Контракт `emphasis` у store.** Масив id вузлів (наприклад `category:web`), які сцена показує як «вибрані». Конфігуратор виставляє його з типів рішення в чернетці, поки активний його маршрут, і очищає при виході. На відміну від миттєвого `highlighted` (hover або фокус), це сталий стан; сцена показує обидва, highlight поверх.

**D82. Майстер конфігуратора.**

- Модель і всі тексти (кроки, помилки з лімітами, суми бюджету, лейбли повідомлення) формує сервер через `buildWizardLabels`. Клієнт отримує JSON-пропси, без шару контенту, словників і ICU у браузері.
- Помилки показуються після «Далі», а не під час введення: `aria-invalid`, `aria-describedby`, фокус на першому невалідному полі. Після переходу на інший крок фокус стає на його заголовок.
- Чернетка зберігається через 300 мс після зміни і при виході зі сторінки.
- «Почати спочатку» вимагає інлайн-підтвердження; фокус ставиться на «Скасувати».
- `?add=` читається з `location.search` в ефекті, тож Suspense не потрібен.

**D83. Синхронізація майстра з чернеткою запиту (D66).**

- Чернетка запиту дзеркалить вибрані в майстрі послуги. Додавання й зняття в майстрі змінюють її, «Почати спочатку» очищає обидві.
- Передзаповнення ідемпотентне; повідомлення з’являється, лише коли додано нові послуги.
- Вибрані типи рішення стають `emphasis` сцени (D81) і очищаються при виході.

**D84. Крок підсумку.**

- У textarea — повний текст повідомлення; саме його копіює «Скопіювати текст».
- Посилання t.me несе версію в межах бюджету URL. Поки текст не змінено, це компактна версія чи версія з обрізаним коментарем; після редагування — відредагований текст, обрізаний до бюджету. Якщо текст скорочено, з’являється попередження.
- «Надіслати в Telegram» — справжнє посилання з `target="_blank"`. «Відкрити чат» і «Скопіювати текст» показуються завжди.
- Без налаштованого username лишається тільки копіювання з поясненням.
- Сабмітер без посилання (`ApiSubmitter`) отримує кнопку «Надіслати»; інтерфейс `LinkLeadSubmitter` + guard `isLinkSubmitter`.

**D85. RequestToggle за APG (уточнення D67).** Доступна назва кнопки стала — «Dodaj do zapytania»; стан передає `aria-pressed`, візуально — ✓ і акцентний стиль. Live region лишається. Ключ `service.addedToRequest` видалено.

**D86. Вибір у конфігураторі в сцені (D81).**

- Поки активний маршрут конфігуратора, вузли з `emphasis` мають сталий стан «вибрано»: ядро, гало й орбіти світяться яскравіше (0,6) і не тьмяніють разом із мережею.
- Від кожної вибраної категорії до маяка йде світна дуга з градієнтом від кольору категорії до кольору маяка; по ній до маяка біжать пакети даних та імпульси.
- Маяк змішує лише кольори вибраних категорій.
- Hover і highlight лишаються поверх (1,0).
- Зміни плавні (300 мс, smoothstep); у reduced motion застосовуються миттєво й без імпульсів. На інших маршрутах вибір не показується.
- Камера віддаляється вздовж напряму фокусу маяка, щоб маяк і всі вибрані категорії вмістилися в safe rect з урахуванням idle-гойдання. Ближче за фокус маяка і далі за огляд вона не йде.
- Якщо всі не вміщаються, категорії додаються від найближчої до маяка.

**D87. `emphasis` у портфоліо (розширення D81).**

- На маршруті портфоліо UI виставляє `emphasis` в id кейсів, що відповідають активному фільтру категорії (`project:<slug>`); без фільтра — `[]`.
- Сцена підсвічує ці об’єкти скупчення й приглушує решту.
- При виході з маршруту `emphasis` очищається, як і в конфігураторі.

**D88. Фільтр портфоліо.**

- Стан фільтра — у query `?category=`. Чипи — звичайні посилання з `replace` і `scroll={false}`; без JS статична сторінка показує всі кейси.
- Query читається на клієнті через `useSearchParams` у Suspense, бо статичний експорт не має query під час запиту; сервер рендерить нефільтрований список.
- Чипи є лише для категорій, де є кейси. Кількість результатів оголошує polite live region (тексти для всіх кількостей готує сервер).
- `emphasis` — відфільтровані кейси (D87); без фільтра — порожній масив.

**D89. Картки-об’єкти й сторінка кейсу.**

- Скляні картки: акцент першої категорії, рік, назва, короткий опис у 2 рядки, до 4 чипів стеку. Hover і фокус підсвічують `project:<slug>` у сцені.
- На сторінці кейсу «← Portfolio» — перша крихта-кнопка.
- Порядок блоків: факти → задача, рішення, результат → демо → галерея → стек → послуги.
- Попередній і наступний кейс ідуть по колу й відкриваються через `replace` — так само, як ←/→ і свайп.

**D90. Демо кейсів.**

- iframe: спершу фасад, сторінка вантажиться лише після кліку. Далі `loading="lazy"`, `sandbox="allow-scripts allow-same-origin allow-forms"`, `referrerpolicy="no-referrer"`, фокус на iframe, посилання «у новій вкладці».
- Відео: `preload="none"`, `controls`, `muted`, `playsInline`, без автозапуску взагалі.
- Мокапи — HTML/CSS (чат, дашборд, бронювання, магазин) з нативними кнопками й радіо; тексти й числа готує сервер.

**D91. Галерея.**

- Заглушки — SVG із `scripts/portfolio-placeholders.mjs` (детерміновані, ≈3 КБ, без тексту); тест перевіряє наявність, розміри й ліміт 8 КБ.
- Зображення — `<img>` з `withBasePath`, width і height, `loading="lazy"`. next/image не використовується: з `unoptimized` він не додає basePath до рядка src.
- Lightbox відкладено.

**D92. Дані-заглушки портфоліо.**

- Кейс `logistics-document-ai` демонструє iframe на https://example.com/. Відео підтримують схема й компонент, але даних для нього немає.
- ~~Превʼю з чернетками: `SHOW_DRAFTS=true npm run build:preview`~~ — замінено D110: `npm run build:preview -- --drafts`.

**D93. Портфоліо як обсерваторія-архів.**

- На маршруті портфоліо камера летить у скупчення. Перед ним стоїть злегка вигнута стіна карток-об’єктів, по одній на кейс, навколо — три повільні кільця обсерваторії.
- Розкладка — чиста функція від кількості кейсів (рядів ≈ √(n/1,4), останній ряд по центру). Новий кейс не потребує змін у сцені.
- Картка — скляна пластина з голографічним лицем. Колір і емблему дає головна (перша) категорія; емблему вибирає її стиль ядра: кристал, страти, шестерня, нейронний вузол, паперовий літачок. Кожна категорія додає кольорову мітку.
- Огляд вписує всю стіну в safe rect анфас. Фокус кейсу вписує його картку (≈1/1,5 висоти); сусіди тьмяніють до 30 %, зорі між камерою й карткою гаснуть.
- Без кейсів камера показує сплячий кластер у кільцях із постійною міткою «незабаром».
- Hover (3D або `project:<slug>`) підсвічує картку й показує мітку в стилі NodeLabels. Клік — push, із фокусу кейсу — replace. Хіт-зони активні лише після польоту.
- Фільтр (D87): картки з `emphasis` підсвічуються, решта тьмяніє до 22 % (≈300 мс, у reduced motion миттєво).
- Архів змонтований лише у фокусі або під час польоту. Матеріали — у кеші Experience, prewarm-ключ `archive`, LOW_QUALITY для всіх нових шейдерів.

**D94. Контракти фінального блоку (простий режим, завантаження, інтро).**

- `simpleMode` (`null` | boolean) виставляє лише UI: збережене налаштування користувача, інакше автоматично `true`, якщо немає WebGL 2 API. Поки `true`, `SceneRoot` не монтує 3D. Рішення ухвалюється до першого рендеру, щоб не було «блимання».
- `bootProgress` 0 → 1 публікує сцена грубими кроками: чанк завантажено, перший кадр, всесвіт скомпільовано, показано. UI показує з нього невеликий індикатор, що не блокує вміст: повноекранний екран завантаження сховав би H1 і погіршив би LCP.
- Інтро першого візиту:
  - `introEligible` вирішує UI: головна, перший візит, без reduced motion.
  - Сцена при показі грає політ ≤ 3 с і тримає `introActive`.
  - Кнопка «Пропустити» викликає `skipIntro`, сцена стрибає в кінець.
  - UI позначає візит як побачений.

**D95. Інтро першого візиту (реалізація D94).**

- Політ із глибокого космосу в огляд триває 2,8 с (`power3.out`).
- Грає лише при показі сцени на головній, коли `introEligible === true`, без reduced motion і без `introSkip`.
- `introActive` тримається, поки триває політ; `flight` інтро не публікує, тож hero чекає на `introActive`. «Пропустити» стрибає в кінець, дотик користувача перериває інтро.
- Колишній рух камери при показі на кожному першому завантаженні прибрано: deep links показуються статично з проявою canvas.

**D96. Сигнал готовності `html[data-scene-ready]`.**

- Значення — шлях без локалі. Атрибут з’являється, коли камера осіла на стані URL (focus = шлях, без польоту й інтро) і фокусний вміст скомпільовано й показано: система для маршрутів системи й планети, архів для портфоліо.
- Під час польотів атрибут знімається. Скриншоти й e2e чекають на нього; він замінює ідею `data-archive-ready`.

**D97. Черга компіляції без голодування (V5-01).**

- Термінові завдання (live, boot) виконуються до 12 мс за idle-слот навіть без вільного часу дедлайну.
- Вміст, на якому фокусується URL, компілюється з пріоритетом boot — і при deep link, і при переході.
- Раніше протерміноване термінове завдання компілювало один матеріал за кадр, і при ~4 fps у SwiftShader картки архіву з’являлися через 12–30 с.

**D98. Кадр фокусу планети (MJ1).**

- Камера перебирає боки огляду навколо планети, починаючи з найменшої зміни. Перший прийнятний бік — той, де ядро поза кадром або щонайменше за 1,5 радіуса від досяжності планети; якщо такого немає, береться бік із найменшим перекриттям.
- Пам’ять вибору не дає боку перескакувати, поки планета паркується.
- У фокусі ядро приглушується до 50 %, корона стискається до 55 %. Для внутрішніх орбіт чистий кадр геометрично неможливий — там найкращий варіант плюс приглушення.

**D99. Кадр системи (MJ2).**

- Система вписується за реальними орбітами (вибірки з досяжністю планет) у 90 % вільної ширини й висоти, а не за описаною сферою.
- У низькій вільній смузі (телефон над sheet) камера пологіша, а спокійний рух — гойдання ±0,35 рад замість повного оберту.
- Планети, менші за 16 px, збільшуються на екрані до ×1,8. Ореоли менші (2,4 радіуса), hit-зони — не менше 44 px.

**D100. Конфігуратор і присутність вузлів.**

- Кадр конфігуратора піднято на 8 % висоти, наскільки дозволяє місце над верхнім вузлом.
- З вибором маяк тримає сталу OKLCH-суміш кольорів вибраних категорій; без вибору колір циклічно змінюється.
- Присутність вузла рахується за його світним диском (1,6 радіуса ядра), а не за центром: вузол на краю кадру згасає, а не обрізається.

**D101. Баланс огляду (L-04).** Після вписування вільний запас меншої осі зсуває кадр приблизно на 60 % до центроїда мережі (без далекого портфоліо). Жодна вписана сфера при цьому не виходить за кадр.

**D102. Дрібні візуальні правки сцени.**

- Мітки планет і карток мають ледь помітну темну підкладку.
- Підсвічена орбіта яскравіша, з біжучим сигналом; решта орбіт відступає.
- Шов кільця прибрано (полярні координати у фрагменті).
- Сусідні вузли в системі тьмяніють разом із мережею.
- Емблеми архіву гранчасті й без шуму: CRM — три шестигранні плити, AI — тонкий вузол.
- Картки, що виходять за вільну область, згасають і не беруть кліків.

**D103. Простий режим (реалізація D94).**

- Рішення ухвалюється до першого кадру. Inline-скрипт у `<head>` читає `kabaninno.simpleMode.v1`, перевіряє WebGL2 API і ставить `html[data-simple]`.

**D115. Відкладений 3D на мобільних (BRIEF B2.6) — не відкладаємо.**

- Виміри F3: Lighthouse 13.6, mobile, gzip, медіана 3 прогонів, SwiftShader. Головна при першому візиті — 70 (11 прогонів у діапазоні 69–71), повторний візит — 71, система web — 70, конфігуратор — 71. Простий режим — 100. CLS 0, LCP 1,05 с.

- Запас Lighthouse можна збільшити розбиттям задачі монтування Canvas (≈1,3 с симульованого TBT) і попередньою компіляцією програм bloom (≈1 с) — у беклозі.

**D116. Правило простого режиму (реалізація D115).**

- Примусово, якщо 3D не може працювати: немає WebGL 2 API або є свіжий маркер `kabaninno.webglFailed.v1` (той самий User-Agent, до 30 днів).
- Інакше вирішує явний вибір відвідувача.
- Інакше простий режим вмикають сильні ознаки слабкого пристрою: `deviceMemory ≤ 2`, `hardwareConcurrency ≤ 2` або `saveData`.
- Одна чиста функція `resolveSimpleMode`. Inline-скрипт у `<head>` повторює її, і тест у `node:vm` перевіряє збіг для всіх комбінацій. Доступ до localStorage у скрипті загорнуто окремо, тож заблоковане сховище не зриває рішення «немає WebGL».
- Наслідок: машини з 2 ядрами (деякі CI-раннери) стартують у простому режимі, якщо вибір не збережено.

- Розкладку, кольори й назви дають `content/` і та сама функція розкладки, що й у 3D.

**D131. Рух простого режиму — лише CSS (transform/opacity).**

**D132. Світні ребра лише на гранчастих формах (MJ-F4-01, уточнює D125).** Реєстр форм має ознаку `faceted`: кристал, ікосаедр, октаедр, шестерня, дротик і кластер кубів. **D134. Поріг сяйва не заливає кадр (mi-F4-02, уточнює D124).** Поріг згасання сяйва поблизу камери (0,4) зменшується, коли білборд заповнює кадр, і зникає з покриття 0,6. Порожнеча за сфокусованою планетою лишається темною.

**D138. Бюджети залежать від вибору (A3).**

**D148. Один CTA (A3).** Текст усіх кнопок-CTA — «Dobierz rozwiązanie» / «Find your solution» / «Підібрати рішення» (`home.cta`, `hud.cta`, `portfolio.emptyCta`). **D149. Конфігуратор-діагностика (B1–B2).** Замість форми з 7 кроків — п’ять: **Цілі → Уточнення → Рішення → Бюджет і терміни → Контакт і підсумок**.

- Дані й логіка: `content/configurator.ts` (`goals`, `have`, `complexity`, `budgetLevels`, `consultationLevel`, `maxGoals` = 3, `maxRecommended` = 4); чиста рекомендація `src/lib/configurator/recommend.ts`; чернетка `draft.ts` (`kabaninno.configurator.v2`, старі v1-чернетки не мігруються: форма інша).
- Рекомендація не зберігається списком, а виводиться з цілей і відповідей; власні дії відвідувача лежать окремо: `removed` (прибрані рекомендовані) і `added` (додані з планети, «Додати ще» або вручну). Зміна відповіді перераховує рекомендацію й не губить ці правки. Послуги беруться по рангах між цілями (перша послуга кожної цілі, потім друга…), тож ліміт у 4 не вирізає цілу ціль.

До кожної цілі я додав варіант «Не знаю» (`unknown`, один спільний текст), щоб ніхто не застряг; у першої цілі він і так був у таблиці. «Що у вас уже є?» — необов’язкове, кілька відповідей, «Нічого з цього» виключне. Відповіді з цього питання потрапляють у повідомлення, але рекомендацію не змінюють (у таблиці правил для цього немає).
- Крок 3: «Вам підійде: <категорії через +>», послуги за категоріями з рядком `benefit` (нове поле текстів послуг, ≤ 90 символів, pl/en/uk) і кнопкою «Прибрати»; «Додати ще» розкриває повний список за категоріями. Без послуг (або «Ще не знаю») — текст про безкоштовну консультацію; крок ніколи не блокує. ## Раунд правок №3

**D153. Кнопка «Підібрати рішення» в HUD — за сторінкою, а не за видимістю (A1).** `HeroCtaWatch`, атрибут `data-hero-cta(-visible)` і CSS `.hud-cta` прибрані (скасовує частину D148). Правило — `showsHudCta(section)` у `src/lib/nav.ts`: на головній і на `/configurator` кнопки немає (вона не рендериться, тож правий блок — 2D і мови — притиснутий до краю без порожнього місця), на решті сторінок (послуги, планети, портфоліо, інші) — є. Те саме правило діє на всіх ширинах: у смузі HUD кнопка видима від `lg`, а нижче в смузі для неї немає місця (на 360 px між словесним знаком і правим блоком лишається 8 px, на 390 px — 31 px), тому на телефоні й планшеті кнопка живе в меню HUD і теж зникає на головній і в конфігураторі.

**D154. Шапка конфігуратора (A2).** Видимий текст «Krok X z N» / «Крок X з N» прибрано; лишились «01 / 05», смуга прогресу і замість рядка вкладок — назва поточного кроку (ліворуч від «01 / 05»). Скрінрідери чують «Krok X z N: <назва>» (прихований текст), бо «01 / 05» схований від них. Повернення назад — лише кнопкою «Назад»; ключ `configurator.stepsNav` видалено (навігаційного орієнтира з кнопками більше немає).

**D155. Конфігуратор: новий перший крок «Ваша галузь» (B1).** Кроки: **Галузь → Цілі → Уточнення → Рішення (з оцінкою) → Контакт**; ручний режим «Я знаю, що мені потрібно» пропускає лише «Уточнення» (4 кроки). Крок «Бюджет і терміни» прибрано повністю: бюджетні діапазони, рівні складності (`complexity`, `budgetLevels`, `consultationLevel`), питання «Коли хочете почати?» (`timelines`), ключі `plan.*`, `budget.*`, `timelines.*` і слово «netto» з усіх текстів.

- Чіпи галузей, один вибір; тап одразу веде на «Цілі». «Інше» лишається на кроці й відкриває поле (до 60 символів) з власною кнопкою «Далі». Галузь **необов’язкова**: «Далі» у футері пропускає крок. Інакше відвідувач із планети («Додати до запиту», D151), який одразу потрапляє на «Рішення» без галузі, не зміг би перейти до контакту (`canEnterStep` вимагає валідних попередніх кроків).
- Типові цілі галузей (`industryGoals` у `content/configurator.ts`, 1–2 на галузь, для «Інше» — жодної) — мій вибір, таблиці від власника не було: торгівля → замовлення онлайн, клієнти; послуги → запис, облік клієнтів; краса й здоров’я → запис, клієнти; харчування → замовлення онлайн, швидкі відповіді; освіта → запис, клієнти; нерухомість → клієнти, облік; логістика → менше рутини, цифри; виробництво → менше рутини, облік; IT → менше рутини, цифри. Позначка «Часто обирають у вашій галузі» — частина назви чекбокса, нічого не вибирається автоматично.
- Чернетка: поля `budget` і `timeline` прибрано; сховище `v: 3` під тим самим ключем `kabaninno.configurator.v2`. Чернетка v2 мігрує: бюджет і термін відкидаються, крок `plan` відкривається як «Рішення»; v1 і невідомі версії ігноруються.

**D156. Оцінка ціни й терміну (B1–B2).** Кожна послуга має `pricePLN: [min, max]` і нові `timelineDays` з таблиці власника (`content/categories.ts`; сторінки послуг теж показують нові терміни). Чиста функція `estimate(services)` (`src/lib/configurator/estimate.ts`): ціна — суми min і max, округлені до 100; термін — `max(найбільший, round(0,7 × сума))` окремо для min і max. Показ терміну — як на сторінках послуг (до 10 днів у днях, інакше в тижнях); якщо тижні округлюються до одного числа, показується одне число («2 тижні»). Ціна — `Intl.NumberFormat` мовою інтерфейсу, без копійок, із символом «zł» (`currencyDisplay: 'narrowSymbol'`, як у прикладі власника): pl «1800–4000 zł» (польська норма не групує чотиризначні числа), uk «1 800–4 000 zł», en «zł 1,800–4,000». Блок оцінки під послугами на кроці «Рішення» оновлюється одразу (live region); без послуг — «Ціну й терміни назвемо після короткої безкоштовної консультації». Фрази термінів формуються на сервері (ICU не на клієнті) для всіх чисел, яких може досягти оцінка.

**D157. WhatsApp (B4).** Номер у повідомленні власника не заповнено («+48 ___ ___ ___»), тому `siteConfig.whatsappNumber: ''` і кнопки немає. Коли номер з’явиться (лише цифри з кодом країни), на кроці «Контакт» поруч із «Надіслати в Telegram» стане рівноцінна «Надіслати у WhatsApp»: копіює текст і відкриває `https://wa.me/<номер>?text=…` у новій вкладці, з тим самим бюджетом URL 2000 символів (на десктопі посилання теж іде через обробник протоколів ОС). Якщо видно обидві кнопки, на вузьких телефонах на них лише «Telegram» / «WhatsApp» (повна назва лишається доступною назвою), щоб футер не переносився. Guard збірки порожній номер не перевіряє.

**D158. Повідомлення від першої особи (B3).** Шаблон власника (uk) і переклади content-writer: вітання; «Мене звати …» + «Хочу скористатися послугами KABANINNO.»; галузь (назва з малої літери, абревіатури як є, для «Інше» — слова відвідувача); «Хочу покращити: …» (окремі фрази цілей `goals.items.*.phrase`); одне речення на кожну відповідь (`goals.items.*.sentences.*`, «Не знаю» речення не дає); «Що вже є: …» або окреме речення для «Нічого з цього»; «На сайті мені підібрали: Категорія + Категорія — послуги.»; «Орієнтовно: ціна, термін.»; коментар; «Чи можемо обговорити деталі?». Порожні рядки пропускаються. Рядок консультації замість рішення ставиться, коли послуг немає (зокрема «Ще не знаю»); якщо відвідувач із «Ще не знаю» сам додав послуги, вони показуються. Для посилання Telegram/WhatsApp, якщо повний текст не влазить у 2000 символів URL (українська — ~330 літер), береться стислий варіант: без порожніх рядків, без речень-відповідей і «Що вже є»; далі вкорочується коментар, в останню чергу — увесь текст. «Скопіювати» завжди копіює повний текст.

**D159. Камера конфігуратора (C, scene-engineer).** Замінює пункт про камеру в D86 («камера відходить, доки не вмістяться маяк і всі вибрані категорії») і підйом MN-4. Тепер на `/configurator` кристал-маяк — точка, куди дивиться камера, і він завжди в центрі вільної зони (на телефоні — в центрі смуги між HUD і шторкою, навіть коли вона лише 33 px заввишки). Камера не повертається до вузлів категорій. Кожна вибрана категорія відводить камеру назад уздовж напрямку погляду на 7 % (разом не більше ніж на 20 %, плавно, ~0,8–1 с). З reduced motion вибір камеру не рухає. Нове з’єднання росте від категорії до кристала за 0,7 с з іскрою на фронті; кілька нових з’являються з інтервалом 150 мс. Вузли категорій зазвичай лишаються за кадром, видно лінії, що входять у кристал. На кроці 1 кристал тепер точно в центрі (раніше трохи вище через підйом MN-4). Заміри (`reports/qa/c3-camera/measurements.json`): зміщення кристала від центру вільної зони ≤ 0,3 px на 1920×1080, 1366×768 і 390×844 для 0–3 категорій; розмір ядра 79,4 → 66,2 px (×1,20).

## Раунд правок №5

**D160. Ціни послуг (A1).** `pricePLN` усіх 20 послуг замінено значеннями з таблиці власника (приблизно вдвічі нижче за D156); терміни не змінювались. Формула оцінки та сама.

**D161. Рекомендації без Telegram для pl і en (A2).** Мова — мова інтерфейсу (маршрут `/pl`, `/en`, `/uk`, який вибирається за мовою браузера або вибором користувача). У `content/configurator.ts` — `telegramLocales: ['uk']` і для кожної відповіді, що веде до Telegram-послуги, `servicesNoTelegram` (модель кидає помилку, якщо його немає або якщо в ньому є Telegram):

- продажі через месенджер (`more-clients/messengers`) → AI-асистент;
- замовлення, до 20 товарів (`online-orders/up-to-20`) → лендінг;
- запис і бронювання (`booking/phone`, `booking/messengers`, `booking/unknown`) → вебзастосунок + сповіщення й нагадування;
- підтримка клієнтів (`fast-replies/telegram`, `fast-replies/repeated-questions`) → AI-асистент (дубль прибирається);
- Mini App жодна відповідь не рекомендує, тож заміна «Mini App → вебзастосунок» не знадобилась.

Замість окремого параметра `recommend(answers, locale)` мова враховується при складанні моделі на сервері: `getConfiguratorModel(locale)` віддає клієнту вже списки для цієї мови, тому вся логіка (рекомендація, оцінка, повідомлення, сцена) не потребує ще одного аргументу. Зміна мови — це перехід на інший маршрут: сторінка отримує модель іншої мови, а рекомендація й оцінка перераховуються зі збереженої чернетки (рекомендація не зберігається, D149). У ручному режимі й у «Додати ще» Telegram-послуги лишаються в усіх мовах. Варіант «У Telegram» питання «Як клієнти зазвичай до вас звертаються?» у pl/en тепер «Na WhatsAppie lub Messengerze» / «On WhatsApp or Messenger» (і речення для повідомлення). Кнопка «Надіслати в Telegram» не змінювалась: це канал зв’язку зі студією, а не рекомендація. Тести перебирають усі 3155 комбінацій відповідей (1–3 цілі з усіма варіантами): у pl і en — жодної Telegram-послуги й жодних дублів, в uk — ті самі результати, що й до зміни.
